# 实现方式决定：资源级 Token（2026-09-16）

> 依据：`鸿蒙规范文档/视觉风格/1-色彩设计规范/04-代码示例/背景代码示范.md` 与
> `2-字体设计规范/04-代码示例/文本样式代码示范.md`、`6-圆角参数/04-代码示例`、`7-间隔参数/04-代码示例`。
> 本文件**修正**《设计令牌清单.md》第七节的"待定"，并纠正其中一处单位误用。

## 一、规范给的做法（原文要点）

| 项 | 规范做法 |
|:--|:--|
| 颜色 Token | 放**资源**里：`resources/base/element/color.json`（浅色）+ `resources/dark/element/color.json`（深色），**Token 名称完全相同、只有色值不同** |
| 组件引用 | 一律 `$r('app.color.xxx')`，**不得硬编码色值** |
| 字号 / 行高 / 圆角 / 间距 | 放 `resources/base/element/float.json`，用 `$r('app.float.xxx')` 引用 |
| 字号单位 | **`fp`（font pixel）**，不是 `vp` —— 只有 `fp` 才随系统字体缩放（无障碍大字体要求） |
| 可选封装 | 再包一层 ArkTS 常量类（`TextStyles` / `SpacingTokens` / `RadiusTokens`）便于复用，但**底层仍是资源 Token** |

## 二、因此本项目的实现方式（定案）

1. **结构色/文字色/品牌金/状态色 → `color.json`（base + dark）**，名称即《设计令牌清单》第二节的 14 个语义名
   （`bg_page`/`bg_card`/`text_strong`/`brand_gold_strong`…）；天地盘那 10 个（`pan_*`）同样进 `color.json`。
2. **排印/圆角/间距 → `float.json`**，字号**改用 `fp`**（修正：令牌清单第四节列的是 vp，实际用 fp）。
3. 组件里一律 `$r('app.color.*')` / `$r('app.float.*')`；**唯一允许出现字面色值的地方是 `color.json`** ——
   这条会做成门禁（"未登记字面色值"判据），杜绝再回到 615 处散落色值的老路。
4. **免费版无需单独维护**：`resources/` 整树由 `sync_free_edition.py` 拷贝同步 ✓（但改完必须跑
   `_ets_pipeline.js` 再编免费版 —— 这是踩过的坑：不跑就编出"旧代码却 BUILD SUCCESSFUL" ✗）。

## 三、一个需求层面的取舍（需用户拍板，不阻塞 Token 化）

用 `base` + `dark` 资源 Token 的话，**浅色/深色由系统自动切换** ✓（跟随系统主题）。而用户原本的诉求是
「**默认保持现在的深色**、可选浅色」✗ —— 两者不同：

| 方案 | 说明 | 代价 |
|:--|:--|:--|
| **甲：跟随系统**（规范推荐） | base=浅色、dark=深色，系统切我也切 | 最省事；但用户在浅色系统里打开 App 会直接看到浅色（与"默认深色"不符）✗ |
| **乙：应用内开关（默认深色）** | 应用内选择三档：深色（默认）/ 浅色 / 跟随系统 | 需自管主题状态并**覆盖**资源默认值（实现更重 ✗，但完全符合诉求 ✓） |

**建议**：Token 化（不改观感）先做完 —— 两种方案都要它 ✓；做到开关那一步时你再选甲或乙 ✓。
若你倾向"少写代码、跟系统"，选甲；若坚持"打开就是现在的深色"，选乙。

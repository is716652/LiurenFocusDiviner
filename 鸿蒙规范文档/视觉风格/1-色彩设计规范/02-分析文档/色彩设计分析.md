# HarmonyOS NEXT 色彩设计分析

## 一、网页核心内容概述

该页面是 **HarmonyOS NEXT 官方 UX 设计规范** 中关于「色彩系统」的章节，主要阐述 HarmonyOS NEXT 的色彩设计理念、系统色构成、色彩分层方法，以及 Token 参数化运作机制。

### 1.1 设计理念

HarmonyOS NEXT 的色彩设计强调三点：

- **品牌色的特征性展示**：通过应用自身的品牌色，帮助用户识别当前应用、理解关键事件。
- **系统色彩的对比关系**：利用色彩对比构建界面层级与信息优先级。
- **为所有人群而设计**：体现包容性设计（Inclusive Design），从不同用户群体视角出发。

### 1.2 系统色调与世界观

HarmonyOS NEXT 的系统色调继承「鸿蒙宇宙」世界观，追求**回归本源、纯净和谐**的视觉体验：

| 系统基础色 | 含义 | 作用 |
|---|---|---|
| **宇宙蓝** | 深邃广阔、纯净宁静 | 象征苍穹，奠定系统整体氛围 |
| **雪域灰** | 自然本色、非绝对黑白 | 象征大地，作为卡片背景烘托纯净感 |

> 宇宙蓝 + 雪域灰 配合，使界面呈现「干净、和谐」的整体体验趋势。

### 1.3 应用品牌色的价值

- 让用户时刻感知当前所属应用进程。
- 帮助用户理解和发现关键性事件。
- 结合层次分明的参数信息和组件结构，提升开发者与设计师的协作效率。

## 二、色彩分层构建方法

页面提出色彩分层的核心目标：**构建不同使用场景下的对比关系**。每个颜色都有独立 ID，用于处理层级对比和同层级一致性。

### 2.1 三大设计原则

1. **映射正确的色彩关系**
   - 系统组件默认对应一套分层参数。
   - 若应用自定义组件规格，需重新梳理背景、文本等色彩的映射关系。

2. **保障色彩的可阅读性**
   - 色彩搭配需满足常规阅读对比度。
   - 系统默认颜色保障最小 **3:1 对比度**。
   - 深色模式下色彩映射关系会变化，但这些变化需符合视觉逻辑。

3. **最小化的色彩管理**
   - 通过「常规色四件套」即可搭建系统整体色彩风格。
   - 降低色彩数量，提升系统一致性与维护性。

## 三、Token 参数运作机制

HarmonyOS NEXT 采用 **Design Token** 方式管理系统色彩。参数名称前缀如 `primary`、`on_primary`、`brand`、`container` 等，在浅色与深色模式下使用**相同的 Token 名称**，但可能对应**不同的色值**。

### 3.1 Token 三层架构

```
控件私有参数（最上层）
    ↑
通用语义参数（中间层）
    ↑
通用基础参数（最底层）
```

| 层级 | 名称 | 说明 |
|---|---|---|
| 第一层 | **基础 Token** | 包含 `primary`、`on_primary`、`brand`、`container`、`background` 等基础色，可通过计算延伸出不同对比度色彩，可直接引用或被重新定义语义。 |
| 第二层 | **语义 Token** | 拥有固定场景名称，分为文本类、图标类、组件类、交互事件类，不可随意更改，定义系统中大部分使用场景。 |
| 第三层 | **控件 Token** | 指定控件内某一元素对应的参数，具有唯一性且不可复用，属于组件内部元素名称。 |

### 3.2 Token 机制的优势

- **跨模式一致性**：同一 Token 在浅色/深色模式下名称不变，仅色值变化。
- **层级清晰**：基础 → 语义 → 控件，职责分明。
- **易于扩展**：应用自定义参数可基于使用场景自定义引用链路。
- **协作高效**：设计师与开发者使用同一套语言，减少沟通成本。

## 四、与鸿蒙开发的关系

### 4.1 对开发者的直接意义

| 方面 | 关系说明 |
|---|---|
| **资源使用** | 开发者应优先使用 HarmonyOS 提供的系统 Token/资源，而非硬编码色值。 |
| **深色模式适配** | 通过 Token 名称不变、色值变化的方式，自动适配浅色/深色模式，减少适配工作量。 |
| **自定义主题** | 应用可基于品牌色自定义基础 Token，并通过语义 Token 映射到组件，保持与系统风格一致。 |
| **无障碍支持** | 系统默认保障 3:1 对比度，开发者遵循规范即可满足基础无障碍阅读要求。 |
| **组件开发** | 自定义组件时应参考控件 Token 的命名与引用关系，确保组件内部元素色彩语义正确。 |

### 4.2 在 ArkTS / ArkUI 开发中的体现

HarmonyOS 开发中，色彩通常以 **资源文件（resources/base/theme.json、dark/theme.json）** 或 **系统预定义 Token** 的形式存在。开发者应：

- 避免在代码中写死 `#RRGGBB` 色值。
- 使用 `$r('app.color.xxx')` 或系统提供的语义化颜色资源。
- 为浅色/深色模式分别配置色值，但保持资源名一致。
- 在自定义组件时，参考官方分层参数定义私有控件 Token。

## 五、启示与建议

### 5.1 设计启示

1. **色彩即品牌**
   - 应用应建立专属品牌色，并贯穿全链路，强化用户认知。

2. **少即是多**
   - 用最小化的色彩数量构建整体风格，避免色彩滥用导致界面混乱。

3. **层级优先于美观**
   - 色彩的首要作用是传递信息层级与对比关系，其次才是视觉表现。

4. **包容性设计**
   - 考虑不同人群（如低视力、色弱用户）的阅读体验，保证对比度和色彩语义清晰。

### 5.2 开发启示

1. **Token 化思维**
   - 将颜色抽象为 Token，便于主题切换、多模式适配和后期维护。

2. **语义化命名**
   - 命名应体现用途（如 `primary`、`on_primary`、`container`），而非具体颜色（如 `blue`、`gray`）。

3. **遵循系统规范**
   - 优先复用系统提供的色彩参数和组件，保持与 HarmonyOS 视觉语言一致。

4. **深色模式不是简单的反色**
   - 深色模式下的色彩映射关系会发生变化，需基于 Token 重新梳理，不能简单取反。

### 5.3 项目实践建议

| 场景 | 建议 |
|---|---|
| 新建鸿蒙应用 | 先定义品牌色，再基于官方基础 Token 扩展语义 Token。 |
| 适配深色模式 | 使用相同资源名配置浅色/深色色值，利用系统切换机制。 |
| 自定义组件 | 参考控件 Token 定义组件内部颜色，保证语义唯一性。 |
| 团队协作 | 设计师与开发者共用 Token 命名规范，建立设计系统文档。 |

## 六、总结

该页面不仅是 HarmonyOS NEXT 的色彩设计指南，更是一套**基于 Token 的色彩系统方法论**。它将设计哲学（鸿蒙宇宙、纯净和谐）、视觉规范（宇宙蓝、雪域灰、分层对比）和工程实现（三层 Token 架构）有机结合在一起。

对于鸿蒙开发者而言，理解并遵循这套色彩系统，可以：

- 快速构建符合 HarmonyOS 视觉风格的应用界面。
- 高效实现浅色/深色模式切换与主题定制。
- 提升应用的无障碍体验与品牌识别度。
- 减少设计与开发之间的沟通成本，实现更高效的团队协作。

## 3. 为什么这么设计

### 3.1 动因（设计原点，已并入本文）

古籍案例对新手是**双重门槛**：古文难读、断法链条看不见。最初的设计讨论定的方向是
**「参照游戏主线任务推进，但做的不是游戏剧情，而是沉浸式断课研习」** ——
使用者面对的不是死板的古文与白话解释，而是**自己动手在盘上取证**。三条产品判断：

1. **不弹选择题**：选项框会让用户从「操作盘面」退化成「操作选项」，而六壬研习者要的正是盘面上的手感；
   所以推进靠**点盘面热区**，点错不罚、只给「困惑」式反馈（现实占卜本来就会看错地方）。
2. **一案一剧本**：不做通用模板。通用模板做出来就失去重复趣味性，所以每个案例预设 3–5 个必须点的关键位置。
3. **一局多占**：同一课同时辰，张三问病、李四问财，取象各异 —— 古籍记录的只是**其中一种可能性**。
   把这一点做成玩法，同一个盘就有多条研习路径，重复打开也有新东西。

### 3.2 已确认的四条落地口径（2026-09-10 定案，写作与实现都按此）

| # | 口径 | 为什么 |
|:--|:--|:--|
| 1 | **异占支线只给「取象清单 + 规则/经文依据」，不给断语、也不揭古籍原断**；只有原占支线在「呈上断语」之后才揭原文断语与应验 | 异占是**我们推的**，不是古人断的。混在一起就是拿软件推断冒充古籍，学术与合规双输 |
| 2 | 首个样板案由实施方自选 → 《六壬断案》元集天时 001「韩太守占祈雪」（己卯日寅将酉时） | 原文推导链完整、应期明确（巳时风／未时雨／亥时作雪厚七寸）——**原文每句都能锚到复算盘面**，适合当范式 |
| 3 | 白话解说**由实施方自撰**，不照抄古籍 | 比抄录更合规，也便于统一加「研习参考」口径 |
| 4 | **先做网页原型，跑通后再移植到 App 的案例鉴赏（收费块）** | 推演交互（可点面、反馈、提示节奏）靠试错定型；网页改一行刷新即可，App 每次都要编译上机 |

### 3.3 核心思路（一句话，写案时反复回到这句）

> **剧情不是「写故事」，而是把引擎对某一课已经算出的盘面事实，编排成一条可亲手取证的推演路径。**
> 断语不是编出来的，是从这些事实按古法通则推出来的 —— **谁能复算，谁就是证据。**

由此推出两条不可让步的结构事实（都已被门禁机械化）：

- 每条线索的每个**锚点**必须能在**引擎现场复算**的盘面上命中（落不到即 FAIL）；
- 线索的 `hint` 只给盘面事实与古法通则，**不得抄录本案原文断语**（8 字窗口比对，命中即 FAIL）——
  逼作者把「断」留给用户在揭古断处自己对照。

### 3.4 叙事设计七法（写在《剧情补录方案与样张》§5，摘要）

三幕结构（情境 → 取证 → 呈上断语与揭古断）；线索写成**问句**（先让人想，再给通则）；
异占支线**跨维度**（动象／音信／阻隔／终局／己身／天时，不要三条支线都问吉凶）；
原占**必揭古断与应验**（钩子最强）；事实与推演分开看；**史实不虚构**（缺的留白或标「（原阙）」，不编应验）；
一案一主题（`badge` 标签，如「课体入门」「动象」「阻隔」）。

## 4. 数据结构与真源

### 4.1 案例库 `rawfile/ancient/case_gallery.json`（45 条，数组）

字段（45/45 齐备，除注明）：

| 字段 | 含义 |
|:--|:--|
| `id` / `title` / `source` / `chapter` | 标识、标题（含纪年与课式）、出处（书名+篇目）、所属书 |
| `input` | 课式输入：`mj`（月将）`dg`/`dz`（日干/日支）`hour`（占时）+ 史实纪年 `yearGan`/`yearZhi`/`monthZhi`、`methodHint` |

| `expect` | 引擎复算的期望值：四课、三传（支/遁干/乘将）、旬空、日干旺衰、月支、课体、中黄（`shiGan`/`bianGan`/`bianGong`/`bianLq`/`bianInChuan`） |
| `summary` / `chain` | 证据链摘要与链条 |
| `reasoning[]` | 断语证据链，按 `role` 分 `main`/`support`/`timing`/`risk`/`cross`，每条带 `claim` 与 `evidence[]`（App 内「断语证据链」区就渲染这个） |
| `focus` | 关注点（如 `{hour, yongShen, chuan[], bianGong}`） |
| `topics[]` | 占类（App 列表按此筛选） |
| `routes[]` | **读象通道**（`base`/`duxiang`/`zhonghuang`/`yongshen`/`bifa`）—— 详情页的通道标签 |
| `compliance` | 合规口径说明 |
| `dunKouJing` | 相关遁甲/课经参考 |
| `chapterNo`（5 案）/ `expect校正说明`（2 案） | 可选补充字段 |

### 4.2 剧情库 `rawfile/ancient/case_story.json`（41 案）

```text
{ schema, note, discipline[],
  stories: { "<案例 id>": { caseId, brief, note, asks[ … ] } } }
```

- `brief`：情境（要素**只能取自该案既有字段**，不得虚构人物与结果）；`note`：同课异占说明。
- 一条 **ask（支线）**：`id` / `role`（`original`｜`derived`）/ `topic`（占类词表 23 类）/ `title` / `intro` / `question` /
  `badge`（看点标签）/ `goodWords` / `clues[]`（非空）/ `endings[4]`（**恰好 4 档**）/ `ending`（`{type,text,note,tip?}`，`type` 必须等于 `role`）。
- 一条 **clue**：`{ id, label, small, anchors[], hint }` —— `label` 是**问句**，`small` 是「点哪里」，`anchors` 至少 1 条，`hint` 是通则。
- **锚点 12 种**（`_tests/_test_case_story.js` 的 `switch(an.kind)` 为准）：
  `method`（课体）· `chuan`(+`pos` 初/中/末) · `keg`（四课，形如 `"子/甲"`）· `jiang`（**形如 `"戌/玄武"`**）·
  `hour` · `gong` · `zhi` · `xunkong` · `dayWangShuai`（**填旺衰值本身**，如 `"死"`）· `shensha`（形如 `"巳/驿马"`）· `shiGan` · `bianGan`。
- **写作纪律**（`discipline[]`，机器判）：`derived` 的 `ending.text` 不得含结论、`ending.note` 必写「非古籍原断」并加现实免责；
  全文**不得出现付费字样**（`付费/解锁/会员/VIP/价格/购买/订阅/充值`）。
- **锚点写法硬规则**（跨批次攒下，逐条见 §9.1）：`method` 必带 `ref`=复算课体名；`jiang` 写**天盘支**不写"某宫乘某将"；
  `shensha` 的 `ref` 写引擎全名（含括号），文案写基名；`dayWangShuai` 取复算值。
- **原占支线不写 `ending.text`**：古断与应验由 App 揭 `case_gallery.json` 的 `original`，剧情里只留 `{type:"original", tip:…}`。

## 6. UI 里显示什么

### 6.1 App 侧：案例鉴赏库（收费研习内容，`AncientCaseGallery.ets` + `pages/Ancient.ets`）

**列表页**：「案例鉴赏」标题；按 `chapter`/出处分组；**占类筛选**（读 `topics`）；
每案一行显示标题、出处，带**日期标记**（`dayMarkOf`）与分组（`groupOf`）；空态文案「案例库整理中」。

**详情页**（点一案进入，自上而下）：

| 区块 | 内容 |
|:--|:--|
| 返回与定位 | 「‹ 案例列表」+「研习样例」 |
| 标题 | `title`（含纪年与课式）+ `source · chapter` |
| 读象通道标签 | `routes` 逐项渲染（`routeLabel` / `routeColor` 上色） |
| **原文断语** | `original` —— 宣纸色卡片、红边，明确标注「原文断语」（与软件推断分区） |
| **程序复算 · 专属盘例** | 右上角「旬空 … · 日干…」；`PanDisk` 天地盘；可点锚点（`锚点 <支> · <说明>` + 「清除」） |
| **四课** | 四张 `KegCard`（干上神/日支+乘将），命中锚点时高亮 |
| **九宗门** | 课体相关 |
| **中黄先锋链路** | 中黄（`shiGan`/`bianGan`/`bianGong`/`bianLq`）链路 |
| **断语证据链** | `reasoning[]`：主断（`main`）+ 支撑（`support`）+ 应期（`timing`）+ 风险（`risk`）+ 参看（`cross`），每条带 `evidence[]`；另有**「异断」**标记（并存/分歧对读） |
| **断法链路纲要** | 链条总览（`chain`） |

**App 侧没有的**：卷宗白话情境、占问方向选择、逐条点盘取证、沉思提示、四档结局 —— 即 §4.2 的整套剧情（见 §6.3）。

### 6.2 网页原型：一局多占推演（`UI/壬案推演原型.html`，孵化器）

**主流程**（原型的完整交互流）：卷宗呈情境 →（选占问方向）→ 起课看盘 → 逐条点线索取证 → 呈上断语 → 揭古断。

原型侧的已知设计（见《剧情补录方案与样张》§10）：

- **可点面 `SURFACES`**：课名、三传卡（支/乘将行）、四课卡（干上神/日干）、天地盘宫位（天支行）、地盘宫、事实栏（旬空/日干旺衰/时支）、**该支所在宫位的神煞行**。
- **可点面已「并集化」**：三传卡任一行 → `chuan+jiang`；四课卡任一行 → `keg+chuan+jiang`；
  天地盘格任一行 → `gong+zhi+旬空+该支神煞+该格乘将`；地盘格任一行 → `gong+zhi+该宫神煞+该格天盘支的乘将`。
- **沉思按钮两段式**：第一次给语境提示，第二次给**具体位置**（用户实测卡住后改的）。
- **四档结局**：原型统一为「藏机 → 窥豹 → 得梗 → 贯通」；`endings` 四档目前多为原型统一文案，**分档递进的具体提示语是待扩展点**（第一批清单 §三.3 已向用户点明）。
- **「证据与规则」面板默认收起**，避免一屏密密麻麻。

**实现实况**（`UI/壬案推演原型.html`，135 行；内联脚本 L58–133）：

| 项 | 实况 |
|:--|:--|
| 结构 | **单页六阶段，无路由**：选案 → 选占问 → 起盘 → 点盘取证 → 立断 → 揭结局；状态量 `cur/started/askIdx/found/thinkIdx/submitted`，由 `renderAll()`(L124) 就地重绘 |

## 7. 收费边界（为什么它在收费块、怎么守）

**它为什么是收费块**：案例鉴赏是**研习内容**（原文整理 + 复算盘例 + 断语证据链 + 剧情推演），
属于「软件本体免费、研习内容收费」的分界；且 **HAP 就是 zip、rawfile 里的 JSON 是明文**，
随免费包发出去等于公开收费数据。

**三道防线**（`_tools/sync_free_edition.py` 生成免费上架版时执行，`verify_free_edition.py` / `verify_app_pkg.py` 硬断言）：

| # | 机制 | 具体 |
|:--|:--|:--|
| 1 | **入口隐藏** | `FeatureFlags.SHOW_ANCIENT_CASE_GALLERY` 写为 `false`（「古籍案例鉴赏」入口在免费包不出现） |
| 2 | **数据剔除** | 从免费包 rawfile **物理删除** `ancient/case_gallery.json` 与 `ancient/case_story.json` |
| 3 | **不变量断言** | 免费包不得存在这两个文件；且免费版 rawfile 与主版**逐文件比对**，缺失集合必须恰好是这两个（新增收费块只改 sync 一处，断言自动跟随） |

**白名单外一律不动**：`ancient/zhonghuang_jing.json`（中黄五变经全文）属**免费**的「古籍」功能，不在剔除之列 —— 别把两者搞混。
另有 `PayConfig.PREVIEW_FREE` 在免费版写为 `false`（过审版全功能开放、无锁无付费痕迹，与申报「无收费项」一致）。

**文本纪律**：剧情与案例文案**不得出现付费字样**（门禁黑名单：`付费/解锁/会员/VIP/价格/购买/订阅/充值`）——
收费是商店与权限层面的事，不在界面文案里喊。

**在架版现状（2026-09-20）**：**1.0.5 已上架**，上架形态是免费版 ——
即**在架包里既没有本块入口、也没有本块数据**；这一点由出包前置的 `verify_free_edition.py` 与包级
`verify_app_pkg.py` 逐条断言守住（本块内容随主版与未来的收费形态走）。

## 9. 写案手册（摘要，完整契约见《剧情补录方案与样张》§2、§10）

**一案六步**：

```text
① 复算    node _tools/case_story_facts.js <案例 id>   # 课体/四课/三传(支+遁干)/乘将/旬空/旺衰/神煞/助日
② 定 brief 用 input 的月将·日干支·占时 + original 的情境与出处，两三句，不虚构
③ 定 asks  1 条 original + N 条 derived（占类取 23 类词表；derived 跨维度）
④ 写 clues 每条：问句 label → 点击位置 small → anchors（复算事实）→ hint（通则，不抄原文）
⑤ 写 ending original 揭古断+应验；derived 列取象清单 + 「非古籍原断」+ 现实免责
⑥ 校验    node _tests/_test_case_story.js  →  python _tools/export_case_story_web.py
```

**硬规则：锚点必须「可点可达」**（用户实测卡住换来的）：每条线索的锚点必须在原型里**存在对应的可点位置**，
否则玩家点遍全盘也触发不了。`small` 只需点到「哪一格/哪一传/哪一课」，**不必指定到行**；
若某条线索非要「点某一行」才触发，说明**锚点与可点面不匹配，应改锚点，而不是改指引文字**。
线索宜**少而深**（3–4 条足够，每条一句问句 + 一处可点位置）—— 用户明确反馈过「不要一上来堆一堆线索让人猜」。

**四个已踩的坑**（写案时对照）：

1. **锚点形状凭直觉写** → 校验器一次报 44 条（`jiang` 要 `"支/将"`、`dayWangShuai` 填旺衰值、`chuan`/`hour` 必带 `ref`）。
2. **抄别案的事实**（把别案的「天马在辰」抄进本案）→ 锚点校验抓到锚点，但**文案里的错要靠审计器**（为此补了「煞在支」判据）。
3. **判据自身的 bug**：煞名含括号导致捕获组错位、44 处全误报 → 改「泛匹配 + 取最长且在煞名表内的后缀」。
4. **全库字符串替换改数据** → 连带改坏别案（韩太守案天马确在辰）→ **改数据必须按案 id 作用域**。

### 9.1 第三～七批攒下的纪律与坑（**原只存在于各批次《审阅清单》，已并入本节**）

| # | 纪律 / 坑 | 出处 |
|:--|:--|:--|
| 1 | **`method` 锚点必须带 `ref`，且等于复算课体名**。不带 `ref` 时闸门只验「有课体」不验对错 —— 第四批曾把「涉害」写成「重审」而两道闸门都没拦住，靠人核复算行才发现。**原文自标多个课式名时只认复算那一个**（第七批 004 案原文标「元首，元胎」，锚点只认元首） | 第四批、第七批 |
| 2 | **乘将挂在「支」上，不挂在「宫」上**：`jiangAt(z) = jiangMap[gongOf(tp, z)]`。锚点一律写**天盘支/将**（`寅/青龙`）；文案凡指宫位，改写为「X 宫之天盘为 Y」，不要写成「X 宫乘某将」 | 第五批(坑2)、第七批(坑4) |
| 3 | **神煞三件套**：锚点 `ref` 写引擎**全名**（含括号，如 `旬癸(闭口)`）、文案写**基名**（`旬癸`）、句式一律「**X 宫带 A、B**」（不要写「煞在支」，别让支与煞名紧挨）。干煞（日德/日禄/皇书…）**按日干按复算查表**，不套「甲禄在寅」式通例（亡盗案日德在申，不在卯） | 第三批(坑)、第四批(附带)、第五批(坑3)、第六批(坑3) |
| 4 | **神煞必须以「校验器口径」复算**：`_test_case_story.js` 起盘只传 `yearGan \\|\\| ''`，年干支写在 `yg`/`yz` 的案，其年干系神煞（皇书等）不在校验器盘上 —— 照工具口径复算会锚空 | 第三批 |
| 5 | **`dayWangShuai` 的 `ref` 取复算返回值**（`c.dx.dayWangShuai`），**不能照 `旺衰休囚死.json` 月令表查**（第四批两案按表查都错） | 第四批、第五批(坑4) |
| 6 | **原占支线不写 `ending.text`**：古断由 App 揭 `case_gallery.json` 的 `original`，剧情只留 `{type:"original", tip:"揭古断与应验"}`，原断写进 `tip`，`note` 标出处与「原文未载应验」。审计器与校验器口径不同处，**以更严的校验器为准** | 第六批(坑1) |
| 7 | **`hint` 引经文不得「将名连写」**：「初传太常，中传六合」这类四字连写会命中 8 字窗口而 FAIL —— 换语序或加字 | 第六批(坑2) |
| 8 | **同一案内不同支线可以有同名 `clue.id`**：批量改写的键必须细到**支线内**（`"askId/clueId"`），写入前自检「所有键必须命中，未命中即拒绝写入」（复建案 `chu`/`mo` 曾被改到另一条支线） | 第六批(坑4) |
| 9 | **同一日干支的案必须一案一案独立复算**，绝不能凭「上一条的思路」往下写（第七批三案同为丙寅日，把 004 的 `巳寅亥` 写成 042 的三传 → 6 条 FAIL） | 第七批(坑1) |
| 10 | **随包 `case_story.json` 是 CRLF**：字符串切片插入必须带 `\r\n`；批量插入改用**纯 JSON 往返**（parse → 删同名键 → 末尾追加 → `stringify`），否则重复插入会留下同名键、出现「明明改好了却还 FAIL」。`UI/_data/case_story.js` 是 LF（生成物），属正常 | 第七批(坑2) |
